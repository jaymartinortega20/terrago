# Decisions log

Every time `SPEC.md` is silent or ambiguous, the choice made and why, in one line each. Newest first.

- **2026-11-02 — Client-side AUTO loop (task #82, part 2 of 2) is a standalone `AutoLoop` class (`client/src/world/autoLoop.ts`) driven once a frame from `WorldScene.update`, scoped to just two decisions: which monster to target, and when to drink a potion — not combat itself.** The key realization that shapes the whole design: `Room.tickPlayerCombatAndInteraction` (server-authoritative) already chases into range and auto-attacks every tick for as long as `player.targetId` stays set, regardless of whether "AUTO mode" is on — a manual click into combat already fights to the death with no further input (confirmed live pre-AUTO). So AUTO's own job is narrower than SPEC.md section 8's "scan/target/move/attack loop" reads at first glance: `move`/`attack` are already happening; AUTO only decides *which* target and *when to heal*.
  - *No new protocol surface needed.* Two things SPEC.md's target-priority rule requires - "a monster currently attacking the player" and "skip monsters another player is already fighting" - sound like they'd need the server to expose per-player combat state, but `combat:result` is already broadcast room-wide (`broadcastToRoom(msg, null, true)`), so `AutoLoop` just listens to `GameState.onCombatResult` and keeps two small `Map<entityId, lastSeenAt>` caches (one for "hit me", one for "hit by another player") with their own short time windows (`BALANCE.combatStateDurationMs` / a local 4s constant) rather than anything persisted server-side. Likewise, "current target" has no `self:state.targetId` field - `AutoLoop` tracks its own belief, invalidated exactly when that entity's snapshot leaves `GameState.entities`, which already happens in every case that matters (monster death/despawn, or a map change via `scene.restart()` on player death/respawn).
  - *Potion auto-use ignores the manual-override window; targeting doesn't.* SPEC.md's "any manual move or target command takes over immediately; AUTO resumes 2s later" bullet is specifically about targeting, and nothing suggests a player who just clicked away from a fight wants their HP% auto-potion to also pause - so `update()` calls `maybeUsePotion` unconditionally every frame and only gates `maybeRetarget` behind the `autoResumeDelayMs` window.
  - *Scope cut, not a gap*: `findPotionSlot` only ever matches an HP need (`ITEMS[id].healHp`) - no resource-restoring consumable exists anywhere in `shared/config/items.ts` yet, so a resource-only need simply finds nothing, same as an empty hotbar. Revisit once such an item is added.
  - *Testing note*: `noteManualInput()`/`setManualTarget()` take an optional `nowMs` (defaulting to `performance.now()`) specifically so `autoLoop.test.ts` can drive them with the same injected clock `update(nowMs)` already took - without it, a test calling `noteManualInput()` then `update(2100)` couldn't deterministically assert the override window's edge, since the real wall clock and the test's synthetic timeline would be two different numbers.
  - *Verified*: 18 new `autoLoop.test.ts` cases (targeting on/off, nearest-reachable pick, scan-radius cutoff, unreachable-tile skip, no-redundant-retarget, retarget-on-target-loss, attacking-me priority over distance, miss doesn't count as aggro, skip-monster-fought-by-another, manual-target recognition, override-window withhold-then-resume, potion threshold/cooldown/manual-independence/no-match-found) plus the full existing suite - 339/339 passing. Live via Playwright (fresh register → Oakhaven → portal to Whispering Fields → AUTO on): confirmed via direct WebSocket outbound sniffing that `target:set` fires with zero manual input and the player visibly walks into and fights a Slime; confirmed `hotbar:use` fires automatically (×2 over 7s, respecting the 1s cooldown) after drag-assigning a potion to hotbar slot 1 and setting a generous 90% HP threshold; confirmed a manual click on a different, precisely-identified (via sniffed `world:snapshot` tile coordinates) Slime immediately sends `target:set` for that monster, overriding AUTO's own pick. Zero console errors across both runs.

- **2026-11-02 — Damage floaters (task #82) are a kind-agnostic `DamageFloaters.spawn(container, kind, amount)` in `client/src/world/damageFloaters.ts`, driven entirely by `GameState`'s existing `onCombatResult` signal plus a new `onHeal` one, with no new WorldScene-owned per-entity state.** `handleCombatResult`/`handleHeal` (WorldScene) just resolve the attacker/defender id to whichever view is already rendering it (`localView` or a `remotes` entry - added a small `resolveEntityView` helper since both combat:result and combat:heal need the same lookup) and hand its `.container` to the floater spawner; the floater itself free-floats upward from a position snapshot rather than tracking the entity afterward, same as every MMO's damage numbers. Styling follows SPEC.md section 11's damage-feedback table directly: white pop-and-float for a normal hit, large gold numbers for a crit, italic "cursive" text for Miss/Lucky (perfectDodge), green for heals.
  - *Found along the way*: a potion heal (`handleHotbarUse`) had nothing telling the client a heal happened or by how much - `self:state` only ever silently reflects the resulting `hp`, which is fine for the HP bar but gives a "Healing: green numbers" floater nothing to trigger on (and no amount to show even if it could). Verified server-side with new `room.test.ts` cases (amount matches the real clamped gain; no message at all when already full) and client-side with a `GameState.test.ts` case mirroring the existing `combat:result` one; the live Playwright pass additionally confirmed the message reaches the browser and renders (a first attempt missed it because the test potion-drink happened after several seconds of UI navigation, during which passive HP regen had already closed the gap - not a bug, just a reminder that this guard does exactly what it says).
  - *Verified live*: Playwright registered a fresh character, walked it through Oakhaven's portal into Whispering Fields, and fought real Slimes - confirmed on-screen: a white "10" on a normal hit, a large gold "8" on a crit, italic "Miss" text on a miss, and (after pre-assigning a potion to the hotbar and drinking it mid-fight) a green "+22" heal floater, all anchored over the correct entity, with zero console errors across several runs covering combat, loot, and a kill.
- **2026-11-02 — `animFor()` (server) now actually reports `'attack'`/`'hurt'`, not just `'walk'`/`'idle'`.** Found while starting task #82 (client combat feedback): `EntitySnapshot.anim` has supported all 7 values since the schema was written, but the server-side `animFor()` helper that produces it only ever checked movement state, so WorldScene's already-built attack/hurt animation playback (task #80's `EntityView`) had no real server signal to ever trigger it on. Fixed with a time-window approach rather than a one-tick pulse, since a single-tick flag could land between two 20Hz snapshots and never reach the client at all: a new `lastHurtAt` field (distinct from the pre-existing `lastAttackAt` - one tracks "I attacked", the other "I was hit") is set on both `PlayerEntity` and `MonsterEntity` only when `performAttack`'s outcome is `'hit'` (never on miss/dodge, so a whiffed swing doesn't fake a hit-react), and `animFor` reports `'hurt'` while `now - lastHurtAt < BALANCE.hurtAnimWindowMs` and `'attack'` while `now - lastAttackAt < BALANCE.attackAnimWindowMs`, hurt taking priority since a hit landing is the more important thing to show even mid-swing. Both windows (250ms/400ms) are sized to match the client's actual paper-doll animation playback length (`client/src/assets/paperDollAnims.ts`'s `ANIM_FRAME_RATE`: hurt = 2 frames @ 8fps, attack = 4 frames @ 10fps) rather than picked arbitrarily, so the server-authoritative anim state lines up with what the animation actually looks like once it plays. Verified with new `room.test.ts` cases driving a real clock through a live Room: a landed hit shows `'hurt'` immediately (ahead of a simultaneous `'attack'` from the same tick's retaliation), falls back to `'attack'` once only the hurt window has elapsed, falls back further to `'idle'` once both have (Slimes are passive and never chase, so there's no `'walk'` to fall back to here), and a guaranteed miss never sets `lastHurtAt` at all even though the swing itself still animates.

All three are easy to retune later since they're plain config, not logic.
- **2026-11-02 — Monster AI for M1 (Slime, `aiBehavior: 'passive'`) does not move or chase.** It sits at its spawn point until a player's attack lands, then retaliates in place at its own attackIntervalMs for as long as the attacker stays within its attack range; it never pursues. This matches "passive" (no proactive aggro) and lets M1 skip monster pathfinding entirely - 'aggressive'/'ranged'/'fleeing' AI (which likely do need movement) arrive with the monster types that use them in M2+.
- **2026-11-02 — Rate-limit thresholds and the 8KB max message size (`server/src/net/protocol.ts`).** SPEC.md's tech-stack table asks for "per-message-type rate limits" but gives no numbers. Picked: auth:login 5/60s, auth:register 3/60s, chat:send 3/2s (the classic abuse/spam vectors, kept tight), movement/targeting/hotbar intents 10-20/s (generous, since legitimate input can legitimately burst), everything else a default of 10/s. 8KB is comfortably above the biggest legitimate M1 payload (chat:send is capped at 200 chars by its own schema) while still being a cheap guard against a client sending huge frames. Revisit with real playtest data once there are real players to generate it.
- **2026-11-02 — Registration grants a starting weapon + potions.** SPEC.md never says a new Recruit is equipped with anything, but M1's acceptance criteria assume fighting Slimes works immediately, and the Recruit has 0 ATK unarmed (formulas.meleeAtk starts from `weaponAtk`). `auth.ts` now equips `recruit_training_sword` and gives 3 `potion_hp_small` on registration.
- **2026-11-02 — No separate character-creation step in v1.** `auth:register` (shared/src/schemas.ts) only carries username+password, and the spec caps v1 at one character per account, so registration creates the Recruit character immediately, named after the username. A character-naming/rename flow can be added later without touching this message shape.
- **2026-11-02 — Session tokens are in-memory, not persisted.** `server/src/auth/auth.ts` keeps a process-local `Map<token, {accountId, characterId}>`. A server restart invalidates all sessions and clients just log in again — acceptable for v1 since nothing in SPEC.md promises reconnect-without-password across a server restart. Revisit if that guarantee is ever asked for.
- **2026-11-02 — Password hashing: argon2.** Spec allows "argon2 or bcrypt". Picked argon2 (the stronger, modern default) over bcrypt since both installed and ran cleanly in the dev sandbox (verified: native prebuilt binary downloads fine once npm is forced through the environment's HTTPS proxy — see the npm-proxy note below).
- **2026-11-02 — SQLite via `better-sqlite3`, as specced.** Confirmed it installs and loads in this sandbox (prebuilt native binary, no compilation needed). Node 22's experimental built-in `node:sqlite` was considered as a zero-dependency alternative but rejected for now: its API differs from `better-sqlite3` and it's still flagged experimental, so sticking with the spec's named package is the safer default. Revisit only if `better-sqlite3` ever fails to install in a future environment.
- **2026-11-02 — Dev-environment note, not a design decision: npm proxy.** In this sandbox, `npm install` fails with `ENOTFOUND registry.npmjs.org` unless run with `npm_config_noproxy="" NO_PROXY="" no_proxy=""` prefixed, because the environment's default `no_proxy` list (meant for environments with direct registry access) excludes the registry host even though this sandbox has no direct DNS/internet — only the local HTTPS proxy works. If a future session hits the same `ENOTFOUND` error on `npm install`, apply the same env override rather than concluding the registry is unreachable.
- **2026-11-02 — Monorepo tool: plain npm workspaces, no extra build orchestrator (Turborepo/Nx).** Spec only asks for "one npm-workspaces monorepo". `shared` is consumed as TS source directly by both `server` (via `tsx`) and `client` (via Vite, which transpiles TS natively) — no separate compile step for `shared` in dev, keeping the one-command `npm run dev` simple. `server` gets its own `tsc` build step for production.
