# Decisions log

Every time `SPEC.md` is silent or ambiguous, the choice made and why, in one line each. Newest first.

- **2026-11-02 — `GameState.entities` is cleared on a mapId change, not just on `reset()`.** Found while designing WorldScene's remote-entity bookkeeping (task #80): a portal/Waystone/`/tp` crossing changes which Room tracks the player, and the OLD room has no way to send this client explicit `left` events for entities it can no longer see - it simply stops tracking this player at all (`Room.leave()`). Without clearing, those entities would sit frozen in `GameState.entities` forever, and WorldScene re-seeding itself from `entities` on scene start (to pick up anything that arrived before the scene existed) would resurrect them as ghosts on the new map. `GameState.handleServerMessage`'s `self:state` case now clears `entities` whenever the incoming `mapId` differs from the previously known one (not on every `self:state`, which fires on ordinary stat/level changes too).
- **2026-11-02 — Relocated `movement.ts` (`setMoveTo`/`setMoveDir`/`stepMovement`/`stopMovement`/`facingFromVector`/`distanceTiles`) from `server/src/sim/` into `shared/src/`.** Found while starting WorldScene's client-side prediction (task #80): SPEC.md section 2 asks for A* to live in `shared/` "so the client (path preview) and server (authority) run identical code" - but continuous movement *stepping* (path-following, WASD axis-collision) is exactly the same kind of pure, networking-free logic, and it was already trapped in `server/`, unreachable by the client, even though it had zero server-specific dependencies (only `@terago/shared`'s own `findPath`/`createTileGrid`/`Facing`/`MapDef`/`TileCoord`). Moving the file (and its test) rather than hand-duplicating it into the client means the client's movement prediction is *provably* identical to the server's authoritative stepping, not just visually similar - the same bar SPEC.md sets for pathfinding, now applied consistently to the rest of movement. `room.ts` now imports these from `@terago/shared` like everything else it uses from there, rather than a relative `./movement.js`. No behavior changed; all 271 tests still pass unmodified (only import paths changed).
- **2026-11-02 — Added `mapId` to `self:state`; no separate "you changed maps" message.** Found while starting WorldScene (task #80): the client had no way at all to learn which of the 12 maps it's currently on - `world:snapshot` only carries entity data, and nothing else names the map either. Rather than adding a new message type, `mapId` was added to the existing `self:state` payload, since `Room.join()` already unconditionally calls `sendSelfState` on every join - including the `toRoom.join()` inside `World.moveCharacterToMap`, the single helper portals/`/tp`/Waystone travel all share - so a portal crossing already re-sends `self:state` with nothing extra to wire up. Verified live by the existing portal-transition test in `world.test.ts`, extended to assert the post-transition `self:state` actually carries the new `mapId`.
- **2026-11-02 — Scene flow is Boot → Login → (Intro | World), decided by server-authoritative `self:state.introSeen`, not a client-stored flag.** SPEC.md's "on later logins the intro is skipped" requires knowing *whose* login it is before the skip decision can be made, so login has to happen before the intro-or-not branch - `LoginScene.submit()` connects, authenticates, waits for the `self:state` message that always follows `auth:result` (`Room.join` sends it synchronously), and calls `scene.start(self.introSeen ? 'World' : 'Intro')`. A client-side localStorage flag was considered and rejected: it would desync from the server's real `characters.intro_seen` column (e.g. a second device, or a future "replay from Settings" action that SPEC.md explicitly allows) in exactly the cases that matter.
- **2026-11-02 — Story intro (task #79): Phaser `Text` typewriter + tweened Ken Burns pan, not a DOM overlay.** Unlike the login form (which needs real `<input>` elements DOM alone can give), the intro is pure presentation - letterbox bars, cross-fading backgrounds, and advancing text - so it stays inside the canvas as three Phaser Scene objects (`rectangle` bars, an `Image` per scroll, one `Text`), keeping the cinematic self-contained and letting Phaser's own tween/animation system drive both the pan/zoom and the fade transitions. Typewriter speed (32 chars/sec) and Ken Burns duration (10s per scroll, continuing even if the player reads faster) are both plain constants with no spec number to match, chosen to read comfortably without feeling slow. The chime SPEC.md describes ("a soft chime plays") is synthesized with two detuned sine oscillators via the Web Audio API (`client/src/audio/chime.ts`) rather than a shipped sound file, matching the project's existing everything-procedural placeholder-content approach - no asset pipeline for audio exists yet, and a sine pair is enough to read as "a chime" without one.
  - *Scope cut, documented so it isn't lost*: SPEC.md section 4 continues past the chime - "the camera glides down from the sky... the player's chibi character plays a short wake-up animation beside the town's central Waystone." That choreography needs a real tilemap and a placed Waystone entity, i.e. task #80's WorldScene rebuild, not the current stand-in - `IntroScene` ends cleanly at `scene.start('World')` and the `wakeUp` pose/animation (already built in `pose.ts`/`paperDollAnims.ts`) is sitting ready for WorldScene to use once there's a real Waystone to stand next to.
- **2026-11-02 — Minimal shared stylesheet (`client/src/ui/styles.css`) introduced with the login form, not deferred entirely to the HUD task.** The login form is the first DOM overlay panel built (task #79) and needed *some* styling to be usable at all; rather than giving it one-off inline styles that task #81's HUD work would later have to either duplicate or rip out, the glassmorphism base classes SPEC.md section 11 asks for everywhere (`.terago-glass`: `backdrop-filter: blur(12px)`, translucent fill, thin border, soft shadow) were factored out now as shared classes, plus the rarity-border classes item tooltips/slots will need later. Task #81 extends this file; it doesn't replace it.: pure canvas-2D drawing functions, not Phaser `Graphics.generateTexture`.** Each generator (`client/src/assets/generators/`) takes a plain `CanvasRenderingContext2D` and draws into it with no Phaser dependency, so the logic is framework-free, typo-checked by `tsc` against the real DOM lib types, and - for `pose.ts` - unit-testable in Vitest with no browser at all. BootScene (task #79) will create an off-DOM canvas per manifest entry, call its generator, and register the canvas with Phaser's texture manager via `textures.addCanvas`.
  - *Paper-doll frame grid*: SPEC.md's "right... mirrored left" means only `down`/`up`/`left` are ever generated; the client flips `left` textures with Phaser's `setFlipX` for `right` (task #80), halving what would otherwise be 4-facing generation.
  - *Manifest split*: `client/assets/manifest.json` hand-lists the bespoke, individually-meaningful assets (tiles, UI icons, intro backgrounds) exactly as SPEC.md section 6 asks ("reference every asset through the manifest... so hand-drawn art can replace it with no code changes"); the paper-doll frame grid is instead enumerated in code (`paperDollManifest.ts`) since it's fully regular (every layer needs the identical facing x anim x frame combinations) - hand-listing 600+ near-identical JSON rows would add no real data-driven value. Swapping a paper-doll layer for hand-drawn art later means pointing its entry in `generators/index.ts` at a loaded spritesheet instead of a draw function, not editing hundreds of manifest rows.
  - *Verification*: rendering correctness here isn't something Vitest can check (no canvas implementation in Node, and pixel output isn't meaningfully assertable even with one) - verified instead with a dev-only visual audit page (`client/preview.html` + `src/previewGallery.ts`, not part of the shipped game) screenshotted with the sandbox's pre-installed Playwright+Chromium. Confirmed: zero console errors generating all ~650 textures, and the composited paper-doll reads clearly as a chibi character across every anim (attack's sword arc and death/wakeUp's fall-and-fade in particular came out well). One known minor polish item: the walk cycle's leg swing is hard to see because the leg pivots sit close to the torso's horizontal center - cheap to retune later (two numeric constants in `paperDoll.ts`'s `drawLegs`) and not worth blocking on.
- **2026-11-02 — Player death: no penalty, respawn at Oakhaven Sanctuary with full HP/resource.** Found while scoping the client's hurt/death animation work: nothing server-side handled a player's HP reaching 0 - it just clamped at 0 with no further consequence, a real gap for anyone actually fighting Slimes. SPEC.md names no death penalty for any milestone, so v1 has none; the player is fully healed, dismounted, and sent to the only monster-free map regardless of which map they died on (`Room.respawnPlayer`, returning a `PortalTransition` that `sim/world.ts` applies exactly like a portal crossing). Revisit if a later milestone's spec text ever asks for EXP loss or item drop on death.
- **2026-11-02 — Added one basic item for each of the helmet/chest/boots/wings slots (`shared/config/items.ts`).** M1's own acceptance criteria require demonstrating "equipping a weapon, helmet, chest piece, boots or wings changes the character sprite" - another gap like `intro:seen`, found while scoping the client's paper-doll work (task #78): only a weapon item existed. These four (`recruit_cloth_cap`/`recruit_cloth_vest`/`recruit_leather_boots`/`tattered_wings`) are common-rarity placeholders with small `def` values, reachable only via `/give` for now since no shop or drop table references them yet - a real acquisition path (the Blacksmith/gear shop NPCs already standing in Oakhaven) is out of scope until a shop system is actually specified.
- **2026-11-02 — Added `intro:seen` (client→server) and `introSeen` (in `self:state`) to the wire protocol.** M1's own acceptance criteria require "on later logins the intro is skipped", and the `characters.intro_seen` column + `PlayerEntity.introSeen` already existed server-side, but nothing exposed it to the client or let the client mark it watched - a gap noticed while starting the client build (task #75) that had to be closed first. Replaying the intro from Settings needed no protocol change: it's purely a client-side "show the scene again" action, never touching server state.
- **2026-11-02 — `server/src/index.ts` env vars: `PORT` (default 8080), `TERAGO_DB_PATH` (default `./data/terago.sqlite`, relative to the server workspace's cwd), `TERAGO_DEV_TOOLS` (`1`/`true` to enable dev commands, matching the `devtools/commands.ts` header comment's own name for this flag).** SPEC.md names none of these explicitly, so they're plain env-configurable defaults rather than hardcoded constants. A connection-level error (a bad message causing `World.join`/`handleMessage`/`leave` to throw) is caught per-connection in `index.ts` and logged rather than crashing the process, so one misbehaving client can't take down every other player's connection; a tick itself throwing is caught the same way inside `sim/tick.ts`.
- **2026-11-02 — `sim/tick.ts` is a thin, swappable driver, not part of `World` itself.** `World.tick(dtSeconds)` stays a plain synchronous method with no notion of real time or intervals, so tests call it directly with whatever `dtSeconds` they want (as `room.test.ts`/`world.test.ts` already did). `startTickLoop()` is the only thing that knows about `setInterval`/`BALANCE.tickRateHz`, and takes injectable timer functions so `tick.test.ts` can drive it with `vi.useFakeTimers()` instead of waiting on real 50ms ticks.
- **2026-11-02 — `sim/world.ts`: `chat:send` is never slash-sniffed; `dev:command` is the only entry point for dev commands.** A client's chat box may let the player type `/level 99` for convenience, but routing that into an actual dev command is the client's job (translating it into a `dev:command` message before sending) — `World.handleChat` always treats `chat:send` text as literal chat, even when it starts with "/", so a player who genuinely wants to say "/level up soon!" in chat isn't surprised by server-side command interception. Verified by a test sending `chat:send` with text `"/level 99"` against a dev-tools-enabled World: the level never changes and the text is broadcast as ordinary chat.
- **2026-11-02 — `sim/world.ts`: one `Room` per entry in `shared/config/maps.ts`, built once in the constructor.** M1 only has two maps so this is cheap, and it means `World` never has to lazily construct or tear down a Room — simpler than an on-demand pool, revisit only if a future milestone's map count makes always-on rooms wasteful.
- **2026-11-02 — `/tp`, portal crossings, and (later) Waystone travel all funnel through one private `World.moveCharacterToMap` helper.** It does `fromRoom.leave()` (persists old position, immediately overwritten) → `repo.saveCharacter(toMapId,x,y)` → `toRoom.join()` with the *same* `send` callback, so the player's connection is never touched — only which Room owns them changes. Keeps the three features from drifting into three slightly-different reimplementations of "move a character between rooms".
- **2026-11-02 — sim/room.ts simplifications for M1 (several, grouped since they all landed in the same milestone piece).**
  - *AOI radius*: `autoScanRadiusTiles` (20, "about a full 1080p screen") + `areaOfInterestMarginTiles` (4) = 24 tiles, reusing SPEC.md's own description of the first number rather than inventing a separate viewport size, since SPEC.md never gives one.
  - *world:snapshot "updated"*: every currently-visible entity is resent every tick, rather than real per-field dirty-tracking. Simple, correct, and matches "at tick rate" - revisit for perf only if M5's profiling pass actually needs it.
  - *Non-mana resource regen*: Stamina/Momentum/Focus reuse the Mana regen formula with INT standing in for the resource stat, since SPEC.md gives a regen formula only for Mana. Placeholder until each resource's real mechanic (e.g. Momentum building from melee hits, not regenerating) arrives with its job in M2.
  - *Job-level skill points aren't tracked yet*: Job Level ups happen and are EXP-tracked, but the `characters` table has no skill-points column and nothing spends them, since M1's Recruit has no skill tree UI to spend them in (that's M2). Add the column when skills arrive.
  - *`target:set` on another player is a no-op*: SPEC.md's controls table lists "inspect" for clicking a player, but no wire message exists for it (ClientMessage/ServerMessage have nothing to carry inspected player info) - deferred until that protocol piece is actually designed.
- **2026-11-02 — Player move speed, melee range, interact range (`shared/config/balance.ts`).** SPEC.md never states a player tile-per-second speed or attack/interact ranges. Picked 4 tiles/s (a brisk walk relative to the Slime's 1.2 tiles/s, and relative to mount's +50% giving 6 tiles/s), 1 tile melee range, 1.5 tiles interact range (reaches an adjacent diagonal). All three are easy to retune later since they're plain config, not logic.
- **2026-11-02 — Monster AI for M1 (Slime, `aiBehavior: 'passive'`) does not move or chase.** It sits at its spawn point until a player's attack lands, then retaliates in place at its own attackIntervalMs for as long as the attacker stays within its attack range; it never pursues. This matches "passive" (no proactive aggro) and lets M1 skip monster pathfinding entirely - 'aggressive'/'ranged'/'fleeing' AI (which likely do need movement) arrive with the monster types that use them in M2+.
- **2026-11-02 — Rate-limit thresholds and the 8KB max message size (`server/src/net/protocol.ts`).** SPEC.md's tech-stack table asks for "per-message-type rate limits" but gives no numbers. Picked: auth:login 5/60s, auth:register 3/60s, chat:send 3/2s (the classic abuse/spam vectors, kept tight), movement/targeting/hotbar intents 10-20/s (generous, since legitimate input can legitimately burst), everything else a default of 10/s. 8KB is comfortably above the biggest legitimate M1 payload (chat:send is capped at 200 chars by its own schema) while still being a cheap guard against a client sending huge frames. Revisit with real playtest data once there are real players to generate it.
- **2026-11-02 — Registration grants a starting weapon + potions.** SPEC.md never says a new Recruit is equipped with anything, but M1's acceptance criteria assume fighting Slimes works immediately, and the Recruit has 0 ATK unarmed (formulas.meleeAtk starts from `weaponAtk`). `auth.ts` now equips `recruit_training_sword` and gives 3 `potion_hp_small` on registration.
- **2026-11-02 — No separate character-creation step in v1.** `auth:register` (shared/src/schemas.ts) only carries username+password, and the spec caps v1 at one character per account, so registration creates the Recruit character immediately, named after the username. A character-naming/rename flow can be added later without touching this message shape.
- **2026-11-02 — Session tokens are in-memory, not persisted.** `server/src/auth/auth.ts` keeps a process-local `Map<token, {accountId, characterId}>`. A server restart invalidates all sessions and clients just log in again — acceptable for v1 since nothing in SPEC.md promises reconnect-without-password across a server restart. Revisit if that guarantee is ever asked for.
- **2026-11-02 — Password hashing: argon2.** Spec allows "argon2 or bcrypt". Picked argon2 (the stronger, modern default) over bcrypt since both installed and ran cleanly in the dev sandbox (verified: native prebuilt binary downloads fine once npm is forced through the environment's HTTPS proxy — see the npm-proxy note below).
- **2026-11-02 — SQLite via `better-sqlite3`, as specced.** Confirmed it installs and loads in this sandbox (prebuilt native binary, no compilation needed). Node 22's experimental built-in `node:sqlite` was considered as a zero-dependency alternative but rejected for now: its API differs from `better-sqlite3` and it's still flagged experimental, so sticking with the spec's named package is the safer default. Revisit only if `better-sqlite3` ever fails to install in a future environment.
- **2026-11-02 — Dev-environment note, not a design decision: npm proxy.** In this sandbox, `npm install` fails with `ENOTFOUND registry.npmjs.org` unless run with `npm_config_noproxy="" NO_PROXY="" no_proxy=""` prefixed, because the environment's default `no_proxy` list (meant for environments with direct registry access) excludes the registry host even though this sandbox has no direct DNS/internet — only the local HTTPS proxy works. If a future session hits the same `ENOTFOUND` error on `npm install`, apply the same env override rather than concluding the registry is unreachable.
- **2026-11-02 — Monorepo tool: plain npm workspaces, no extra build orchestrator (Turborepo/Nx).** Spec only asks for "one npm-workspaces monorepo". `shared` is consumed as TS source directly by both `server` (via `tsx`) and `client` (via Vite, which transpiles TS natively) — no separate compile step for `shared` in dev, keeping the one-command `npm run dev` simple. `server` gets its own `tsc` build step for production.
